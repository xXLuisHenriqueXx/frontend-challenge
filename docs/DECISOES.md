# Decisões de execução

## Etapa 6 — assets, inicialização e auditoria reproduzível

A arte original `src/assets/monkey.png` (1254×1254, 1.885.435 bytes) foi preservada. `scripts/optimize-images.mjs` gera WebP sem perdas em 256/512/768 e 1254 px. O arquivo integral tem 1.276.290 bytes e a comparação dos buffers RGB decodificados é idêntica ao PNG. Os menores usam redimensionamento Lanczos do Sharp, com mesma composição/cores; podem alterar pixels de amostragem sem redesenhar a arte. NftImage escolhe a resolução por srcset/sizes e reserva largura/altura. Hero e primeiros cards priorizam carregamento; cards posteriores e conteúdo editorial usam lazy loading. O preload inicial usa a mesma família responsiva. O logo favicon é um K vetorial local na paleta existente; não é nova ilustração NFT.

As dimensões explícitas corrigem o CLS observado no detalhe mobile, causado pela imagem sem espaço reservado. As novas referências visuais devem ser revisadas por causa da reamostragem; isso não equivale a confirmar fidelidade ao Figma. O projeto já reutilizava a mesma arte nos NFTs, destaques e editorial; essa substituição das imagens do layout continua sendo uma limitação conhecida.

`main.tsx` passa a carregar `app.tsx` e os mocks em paralelo, montando React somente após MSW estar pronto. Continua usando React, Router, Query, Axios e socket.io-client completos; não há página estática, resposta embutida em componente, desativação de recurso ou modo especial para Lighthouse. MSW fica silencioso no build para reduzir logs verbosos da demonstração; os mesmos handlers e eventos permanecem ativos. O code splitting por rota do Router foi preservado.

Tailwind passa a detectar classes somente em `src` com `source("./")`. Sem essa restrição, relatórios Lighthouse e a cópia de instalação limpa eram candidatos à detecção automática e inflavam o CSS. Isso evita que executar auditorias mude o próximo build. A tipografia monoespaçada, cores, layouts e fontes disponíveis foram mantidos; fontes não foram substituídas para melhorar métricas. `robots.txt`, favicon e descrição com acentos corretos completam os metadados locais.

`lighthouse.config.mjs` usa Lighthouse 13.6.0 com perfis simulados padrão, sem excluir categorias/regras ou recursos da página. Cada medição usa Chromium novo com cache frio, cenário success/120 ms e reset de fixtures; páginas início/detalhe, mobile/desktop, três repetições. O executor usa Playwright somente para lançar/fechar Chromium e Lighthouse pelo CDP para medir. Fechar o browser por completo evita processos remanescentes observados com chrome-launcher no Windows. Relatórios finais, versões, condições, métricas e hash SHA-256 dos inputs estão em reports/lighthouse/final. O ambiente é uma estação Windows compartilhada, sem isolamento de CPU/memória; resultados são medições locais, não garantia universal.

A validação de instalação limpa usa uma cópia de fontes em `.verification/clean`, criada sem node_modules, seguida de npm ci. Isso evita interromper servidores previamente abertos no workspace. O cache npm é reutilizado apenas para baixar pacotes verificados pelo lockfile; node_modules é criado do zero. O Chromium do Playwright já instalado é indicado por caminho absoluto. As evidências finais e as metas não atingidas são registradas em AUDITORIA.md.

O build continua emitindo aviso de chunk acima de 500 kB, incluindo dependências da interface. Não foi removida funcionalidade nem reduzida a stack para ocultar o aviso. Configuração de fallback Vercel foi adicionada, mas publicação/URL pública e validação no host continuam pendentes. Inspeção humana permanece pendente: Browser retornou “No browser is available” e lista vazia nesta etapa.

O código existente usa Vite + TanStack Router em modo SPA, não TanStack Start SSR. Esta etapa preserva esse modo para manter os componentes e o visual existentes. Dados remotos são obtidos no cliente com Query + Axios; toda simulação REST usa MSW, sem API routes ou server functions. Não foi introduzida infraestrutura de SSR.

MSW fica ativo por padrão tanto no desenvolvimento quanto no build de demonstração; pode ser desativado explicitamente por VITE_MOCKS=false. Sua inicialização precede a primeira consulta e protege acesso a window. O worker e as fixtures são locais; não é necessário backend privado. O deploy deve oferecer fallback de SPA para acesso direto às rotas.

Contratos, cenários, política de cache e limitações estão em API.md, ARQUITETURA.md e MOCKS.md. A etapa 3 integra socket.io-client com o binding MSW, em transporte WebSocket; polling REST permanece apenas como recuperação de pedidos pendentes. Perfil e carteiras seguem as capturas em docs/design e os tokens existentes, com formulários adaptados ao mobile. Nenhuma avaliação visual ou de CLS foi declarada sem navegador disponível.

Títulos por rota, idioma pt-BR, descrição básica e cor de tema foram adicionados. O foco vai ao h1 após carregamento; para headings visualmente ocultos, vai ao main rotulado. A troca somente de parâmetros do catálogo não rouba foco da busca. Background refetches não geram anúncios repetidos; notificações de preço/pedido usam uma região estável e educada.

A implementação do diálogo segue o [padrão modal do WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/) e os testes usam a [integração axe com Playwright](https://playwright.dev/docs/accessibility-testing). Nenhuma regra foi desativada para ocultar violações encontradas.

### Reproduzir a verificação

Instalar dependências e Chromium: `npm install` e `npx playwright install chromium`. Para usar o diretório de browsers deste workspace, definir `PLAYWRIGHT_BROWSERS_PATH=.npm-cache/playwright` antes da instalação. A configuração prefere esse diretório quando ele existe; num checkout limpo, usa o diretório padrão do Playwright e sempre respeita uma variável já definida. No PowerShell, pode-se usar `npm.cmd`/`npx.cmd`.

Executar `npm run test:a11y`. O comando inicia build/preview na porta 3100 e executa seis cenários em cada largura (390, 768 e 1440): axe em nove telas, foco do diálogo, erros locais/API, navegação/títulos/tabs/favorito, reflow equivalente a 200% e reduced motion/skeleton. Para utilizar um preview previamente iniciado na mesma porta, definir `A11Y_REUSE_SERVER=true`. Relatório HTML em `playwright-report/index.html`; os resultados axe são anexados como JSON. Falhas retêm screenshot e trace em `test-results`.

O executor `scripts/run-a11y.mjs` inicia Vite e Playwright diretamente pelo Node e encerra somente o preview que criou. Isso evita o encerramento pendente observado com processos npm/cmd aninhados no Windows. Uma porta já ocupada exige reutilização explícita; nesse caso o servidor externo não é encerrado pelo teste.

O reflow automatizado usa metade da largura CSS como equivalente de layout a 200% e verifica overflow nas páginas públicas e privadas. Isso não substitui inspeção visual humana, zoom nativo com Ctrl+ e testes com leitor de tela. A skill Browser retornou ausência de navegador conectado; a conexão foi solicitada ao usuário para a verificação manual por teclado. Essa etapa manual permanece pendente e não foi apresentada como teste concluído.

A validação final aprovou 18 cenários (seis por largura), incluindo foco após exclusão no carrinho, favorito via Space e compra até recibo. Foram 33 análises axe sem violações nos escopos configurados; resultados e versões estão na atualização da etapa 4 em AUDITORIA.md. O recibo adapta suas linhas em largura CSS inferior a 320 px e permite quebra de identificadores longos, preservando o snapshot e evitando overflow sem truncar informação.
